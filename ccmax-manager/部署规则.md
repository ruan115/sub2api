# CCMAX 部署规则

本文约束 CCMAX Manager 在 `newapi-16c`（`170.106.159.197`）上的发布流程。应用端口固定为 `127.0.0.1:8088` 和 `127.0.0.1:8089`，每次只向非活动端口发布，切流成功后保持该端口运行；下一次发布再切回另一个端口。同机 New API 始终通过稳定入口 `127.0.0.1:18080` 访问 CCMAX。

## 基本原则

- 只发布 `ccmax-manager`，不修改同机 New API 的服务、配置和数据。
- 源码必须先提交并推送到 GitHub 的 `ccmax` 分支；服务器只下载确定 commit 的 GitHub 归档，不接收本地工作区源码包。
- 发布前必须通过 `go test ./...`、`go test -race ./...`、`go vet ./...`、`node --check web/app.js` 和 `git diff --check`。
- 前端资源嵌入 Go 二进制，修改 `web/` 后必须重新构建。
- 生产数据库使用 MySQL，Redis 用于限流和跨实例调度协调。发布前必须创建并验证 MySQL 备份。
- 禁止覆盖 `/etc/ccmax-manager.env`、`/etc/ccmax-manager-secrets/` 和历史备份。
- 禁止直接重启活动端口。必须先启动另一端口、健康检查、切换 Nginx、等待旧 worker 排空，最后停止旧端口。
- 同一轮发布只切流一次，不再把新版本迁回原端口。
- `ccmax.annaapi.com`、`ccmax-direct.annaapi.com` 和 `127.0.0.1:18080` 必须同时指向同一个活动应用端口。
- New API 渠道只能配置 `http://127.0.0.1:18080`，禁止直接配置 `8088` 或 `8089`。

## Nginx 高并发基线

生产机的 `/etc/nginx/nginx.conf` 必须与 `deploy/nginx-main.conf` 保持一致：每个 worker 使用 `65535` 个连接，worker 文件句柄上限为 `524288`。`deploy/nginx-high-concurrency.conf` 安装在 `/etc/sysctl.d/zz-nginx-high-concurrency.conf`，并确保 `/etc/sysctl.conf` 没有重复定义 `net.core.somaxconn`。

调整前后必须执行 `nginx -t`。应用 sysctl 后核对 `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog` 和 `net.ipv4.ip_local_port_range`，reload 后确认错误日志不再新增 `worker_connections are not enough`。

CCMAX OAuth 账号必须继续绑定状态正常的住宅代理，默认上游固定为 `https://api.anthropic.com`；同机调用不得绕到 Cloudflare 域名。

## 一次性安装端口服务

将模板安装到服务器；旧的 `ccmax-manager.service` 在第一次成功切到 `8089` 并排空后停用，此后统一使用模板实例。

```bash
scp deploy/ccmax-manager@.service newapi-16c:/tmp/ccmax-manager@.service
ssh newapi-16c "sudo install -o root -g root -m 0644 /tmp/ccmax-manager@.service /etc/systemd/system/ccmax-manager@.service && sudo systemctl daemon-reload"
```

模板实例分别为：

```text
ccmax-manager@8088.service
ccmax-manager@8089.service
```

## 发布前验证

在仓库根目录执行：

```bash
git status --short -- ccmax-manager backend
git diff --check
(cd ccmax-manager && go test ./... && go test -race ./... && go vet ./... && node --check web/app.js)

BRANCH=ccmax
COMMIT=$(git rev-parse HEAD)
git push origin "${BRANCH}"
git fetch origin "${BRANCH}"
test "$(git rev-parse origin/${BRANCH})" = "${COMMIT}"
test -z "$(git status --porcelain -- ccmax-manager backend)"
```

## 从 GitHub 下载并构建

服务器直接下载 GitHub 指定 commit，归档地址不能使用浮动分支名：

```bash
STAMP=$(date +%Y%m%d%H%M%S)
COMMIT=$(git rev-parse HEAD)

ssh newapi-16c "set -eu
  BUILD=/tmp/ccmax-build-${STAMP}
  ARCHIVE=/tmp/sub2api-${COMMIT}.tar.gz
  GO_BIN=\$(command -v go || true)
  if [ -z \"\$GO_BIN\" ] && [ -x /usr/local/go/bin/go ]; then GO_BIN=/usr/local/go/bin/go; fi
  test -x \"\$GO_BIN\"
  rm -rf \"\$BUILD\"
  mkdir -p \"\$BUILD\"
  curl --fail --location --retry 3 \
    https://codeload.github.com/ruan115/sub2api/tar.gz/${COMMIT} \
    -o \"\$ARCHIVE\"
  tar -xzf \"\$ARCHIVE\" -C \"\$BUILD\" --strip-components=1
  cd \"\$BUILD/ccmax-manager\"
  \"\$GO_BIN\" mod vendor
  CGO_ENABLED=1 \"\$GO_BIN\" build -mod=vendor -trimpath -ldflags='-s -w' -o /tmp/ccmax-manager-${STAMP} .
  sudo install -d -o root -g ccmax -m 0750 /opt/ccmax-manager/releases/${STAMP}
  sudo install -o root -g ccmax -m 0750 /tmp/ccmax-manager-${STAMP} /opt/ccmax-manager/releases/${STAMP}/ccmax-manager
  sudo install -o root -g ccmax -m 0640 \"\$ARCHIVE\" /opt/ccmax-manager/releases/${STAMP}/source.tar.gz
  printf '%s\n' ${COMMIT} | sudo tee /opt/ccmax-manager/releases/${STAMP}/GIT_COMMIT >/dev/null
  file /opt/ccmax-manager/releases/${STAMP}/ccmax-manager"
```

必须确认 `GIT_COMMIT` 与 GitHub 远程 commit 一致，二进制必须是 Linux x86-64 ELF。服务器可以使用 PATH 中的 Go，也可以使用生产机固定安装的 `/usr/local/go/bin/go`；不得上传本地编译产物替代服务器构建。

## 交替端口无感发布

### 1. 确定源端口和目标端口

从 Nginx 当前 upstream 读取活动端口，不依赖人工记忆：

```bash
NGINX_FILES="/etc/nginx/sites-available/ccmax-manager /etc/nginx/sites-available/ccmax-direct /etc/nginx/sites-available/ccmax-internal /etc/nginx/sites-enabled/ccmax-manager /etc/nginx/sites-enabled/ccmax-direct /etc/nginx/sites-enabled/ccmax-internal"
SOURCE_PORT=$(ssh newapi-16c "sudo grep -hoE '127\\.0\\.0\\.1:(8088|8089)' ${NGINX_FILES} | sort -u | sed -E 's/.*://'" )
test "${SOURCE_PORT}" = "8088" -o "${SOURCE_PORT}" = "8089"
if [ "${SOURCE_PORT}" = "8088" ]; then TARGET_PORT=8089; else TARGET_PORT=8088; fi
```

三个站点若解析出多个不同端口，立即停止发布并先修复配置一致性。

### 2. 在目标端口启动新版本

```bash
ssh newapi-16c "set -eu
  sudo install -d -o root -g ccmax -m 0750 /opt/ccmax-manager/ports/${TARGET_PORT}
  sudo ln -sfn /opt/ccmax-manager/releases/${STAMP}/ccmax-manager /opt/ccmax-manager/ports/${TARGET_PORT}/ccmax-manager
  sudo systemctl restart ccmax-manager@${TARGET_PORT}.service
  for i in \$(seq 1 30); do curl -fsS http://127.0.0.1:${TARGET_PORT}/api/health && exit 0; sleep 1; done
  sudo journalctl -u ccmax-manager@${TARGET_PORT}.service -n 100 --no-pager
  exit 1"
```

健康检查失败时停止目标实例，不得修改 Nginx。

### 3. 一次切流

记录 reload 前的旧 worker，然后把三个站点的 available 与 enabled 文件同时从源端口替换为目标端口。生产机上的 `sites-enabled` 可能是独立文件而不是软链接，不能只修改 `sites-available`：

```bash
ssh newapi-16c "set -eu
  pgrep -P \$(cat /run/nginx.pid) | sudo tee /tmp/ccmax-nginx-workers-${STAMP} >/dev/null
  sudo sed -i 's#127.0.0.1:${SOURCE_PORT}#127.0.0.1:${TARGET_PORT}#g' \
    /etc/nginx/sites-available/ccmax-manager \
    /etc/nginx/sites-available/ccmax-direct \
    /etc/nginx/sites-available/ccmax-internal \
    /etc/nginx/sites-enabled/ccmax-manager \
    /etc/nginx/sites-enabled/ccmax-direct \
    /etc/nginx/sites-enabled/ccmax-internal
  sudo nginx -t
  sudo systemctl reload nginx
  test "\$(sudo nginx -T 2>/dev/null | grep -Eo 'proxy_pass http://127\\.0\\.0\\.1:(8088|8089)' | sort -u)" = 'proxy_pass http://127.0.0.1:${TARGET_PORT}'"
```

切流后立即验证：

```bash
curl -fsS https://ccmax.annaapi.com/api/health
curl -fsS https://ccmax-direct.annaapi.com/api/health
ssh newapi-16c "curl -fsS http://127.0.0.1:18080/api/health"
```

### 4. 排空旧连接并停止源端口

```bash
ssh newapi-16c "for i in \$(seq 1 3600); do alive=0; while read -r pid; do kill -0 \$pid 2>/dev/null && alive=1; done < /tmp/ccmax-nginx-workers-${STAMP}; [ \$alive -eq 0 ] && exit 0; sleep 1; done; exit 1"
```

排空后停止旧实例：首次从旧服务迁移时停止 `ccmax-manager.service`，后续停止对应模板实例。

```bash
if [ "${SOURCE_PORT}" = "8088" ] && ssh newapi-16c "systemctl is-active --quiet ccmax-manager.service"; then
  ssh newapi-16c "sudo systemctl disable --now ccmax-manager.service"
else
  ssh newapi-16c "sudo systemctl stop ccmax-manager@${SOURCE_PORT}.service"
fi
```

发布到此结束。目标端口保持活动，不替换、不重启，也不在本轮切回源端口。

## 发布验证

```bash
ssh newapi-16c "systemctl is-active ccmax-manager@${TARGET_PORT}.service; curl -fsS http://127.0.0.1:${TARGET_PORT}/api/health; sudo nginx -t; sudo journalctl -u ccmax-manager@${TARGET_PORT}.service --since '-10 minutes' --no-pager"
```

同时确认：

- 三个 Nginx 站点只指向 `${TARGET_PORT}`。
- `${SOURCE_PORT}` 已停止监听，`${TARGET_PORT}` 保持运行。
- New API 渠道仍为 `http://127.0.0.1:18080`。
- 管理页面已加载新资源。
- `/v1/models`、流式请求和非流式请求均使用测试用户 SK 完成真实回归。
- 日志中没有完整用户 SK、Session Key、Access Token 或 Refresh Token。
- New API 的 `127.0.0.1:3000` 服务状态没有变化。

## 回滚

新端口出现问题时，先重新启动上一端口对应的上一 release，健康检查通过后按同样流程反向切流并排空连接。回滚也只切一次，不恢复数据库备份。

数据库回滚必须先停止两个端口、保留故障库副本，并使用已通过 `gzip -t` 和恢复演练的 MySQL 备份；否则会丢失发布后的新增账号、计费和请求日志。
