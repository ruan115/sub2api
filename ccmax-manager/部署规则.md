# CCMAX 部署规则

本文约束 CCMAX Manager 在 `newapi-16c`（`170.106.159.197`）上的发布流程。线上服务由 `ccmax-manager.service` 管理，正式端口为 `127.0.0.1:8088`。Nginx 同时承载 `ccmax.annaapi.com`、`ccmax-direct.annaapi.com` 和供同机 New API 使用的稳定入口 `127.0.0.1:18080`。

## 基本原则

- 只发布 `ccmax-manager` 产物，不修改同机的 New API 服务、配置和数据。
- 发布源码必须先提交并推送到 Git 远程，再用 `git archive` 从确定的 commit 打包。禁止直接上传或从当前工作区打包源码。
- 发布前必须通过 `go test ./...`、`node --check web/app.js` 和 `git diff --check`。
- 前端资源嵌入 Go 二进制，修改 `web/` 后必须重新构建二进制。
- 不上传或覆盖 `/etc/ccmax-manager.env`、`/etc/ccmax-manager-secrets/` 和数据库备份。
- 生产数据库使用 MySQL，Redis 仅用于限流和调度协调。每次发布前必须触发 `ccmax-mysql-backup.service` 并通过 `gzip -t` 验证新备份。
- `/var/lib/ccmax-manager/ccmax-manager.db*` 是 MySQL 切换前的最终 SQLite 快照，仅供受控回滚，禁止作为生产写库重新启动。
- 禁止直接 `systemctl restart ccmax-manager`。发布必须使用下述蓝绿切流流程，保护长非流请求和流式请求。
- New API 的 CCMAX 渠道必须指向 `http://127.0.0.1:18080`，禁止直接指向会被替换的 `8088` 或临时 `18088`。
- 临时 green 实例必须关闭定时价格同步、Token 刷新和账号健康检查，避免两个实例重复执行后台任务。
- 每次发布保留独立 release、旧二进制备份、数据库备份和 Nginx 配置备份。

## Nginx 高并发基线

生产机的 `/etc/nginx/nginx.conf` 必须与 `deploy/nginx-main.conf` 保持一致：每个 worker 使用 `65535` 个连接，worker 文件句柄上限为 `524288`。`deploy/nginx-high-concurrency.conf` 必须安装为 `/etc/sysctl.d/zz-nginx-high-concurrency.conf`，确保它在系统自带的 `99-sysctl.conf` 之后加载，避免监听队列或本机上游临时端口先于 Nginx 连接数耗尽。

`/etc/sysctl.conf` 不得再重复定义 `net.core.somaxconn`；Ubuntu 的 `sysctl --system` 会在目录配置后再次读取该文件，旧值会覆盖 `zz-nginx-high-concurrency.conf`。

调整前后都必须执行 `nginx -t`。应用 sysctl 后核对 `net.core.somaxconn`、`net.ipv4.tcp_max_syn_backlog` 和 `net.ipv4.ip_local_port_range`，Nginx reload 后确认错误日志不再新增 `worker_connections are not enough`。

同机 New API 到 CCMAX 的请求只能使用 `http://127.0.0.1:18080`。CCMAX OAuth 账号必须绑定状态正常的住宅代理，默认上游固定为 `https://api.anthropic.com`；内部调用不得绕到 `ccmax.annaapi.com`、`ccmax-direct.annaapi.com` 或其他 Cloudflare 域名。

## 构建与上传

每个线上产物必须能唯一追溯到 Git commit。发布前先提交目标修改，在仓库根目录执行：

```bash
git status --short -- ccmax-manager
git diff --check

(cd ccmax-manager && go test ./... && node --check web/app.js)

BRANCH=$(git branch --show-current)
COMMIT=$(git rev-parse HEAD)
test -n "${BRANCH}"
test -z "$(git status --porcelain -- ccmax-manager)"
git push origin "${BRANCH}"
git fetch origin "${BRANCH}"
test "$(git rev-parse "origin/${BRANCH}")" = "${COMMIT}"

STAMP=$(date +%Y%m%d%H%M%S)
SOURCE_ARCHIVE="/tmp/ccmax-manager-${COMMIT}-${STAMP}.tar.gz"
BUILD_ROOT="/tmp/ccmax-manager-build-${STAMP}"
git archive --format=tar.gz -o "${SOURCE_ARCHIVE}" "${COMMIT}" ccmax-manager backend
mkdir -p "${BUILD_ROOT}"
tar -xzf "${SOURCE_ARCHIVE}" -C "${BUILD_ROOT}"

cd "${BUILD_ROOT}/ccmax-manager"
go mod vendor -o "/tmp/ccmax-vendor-${STAMP}"
docker buildx build --platform linux/amd64 --build-context "vendor=/tmp/ccmax-vendor-${STAMP}" -f Dockerfile.release --label "org.opencontainers.image.revision=${COMMIT}" -t ccmax-manager:${STAMP} --load .
CID=$(docker create ccmax-manager:${STAMP})
docker cp "${CID}:/usr/local/bin/ccmax-manager" "/tmp/ccmax-manager-${STAMP}"
docker rm "${CID}"
file "/tmp/ccmax-manager-${STAMP}"
shasum -a 256 "/tmp/ccmax-manager-${STAMP}"

ssh newapi-16c "sudo install -d -o root -g ccmax -m 0750 /opt/ccmax-manager/releases/${STAMP}"
scp "${SOURCE_ARCHIVE}" "newapi-16c:/tmp/ccmax-manager-${COMMIT}-${STAMP}.tar.gz"
scp "/tmp/ccmax-manager-${STAMP}" "newapi-16c:/tmp/ccmax-manager-${STAMP}"
ssh newapi-16c "sudo install -o root -g ccmax -m 0750 /tmp/ccmax-manager-${STAMP} /opt/ccmax-manager/releases/${STAMP}/ccmax-manager && sudo install -o root -g ccmax -m 0640 /tmp/ccmax-manager-${COMMIT}-${STAMP}.tar.gz /opt/ccmax-manager/releases/${STAMP}/source.tar.gz && printf '%s\n' '${COMMIT}' | sudo tee /opt/ccmax-manager/releases/${STAMP}/GIT_COMMIT >/dev/null"
```

必须确认 Git 远程分支的 commit、源码归档文件名中的 commit 和 release 目录内 `GIT_COMMIT` 完全一致。`file` 输出必须为 Linux x86-64 ELF，不能把 macOS/arm64 本地产物上传到服务器。

本机 Colima 内存不足时，不得退回旧二进制。应上传上述 `git archive` 生成的源码归档、`go mod vendor -o` 生成的依赖快照和 Linux amd64 Go 工具链，在服务器临时目录以 `GOPROXY=off CGO_ENABLED=1 go build -mod=vendor` 构建。禁止临时重新打包工作区替代 Git 归档；构建目录只能位于 `/tmp/ccmax-build-${STAMP}`，不能在 `/opt/ccmax-manager` 或数据目录内直接编译。

## 发布前备份

```bash
ssh newapi-16c "sudo install -d -o ccmax -g ccmax -m 0750 /var/lib/ccmax-manager/backups/${STAMP}"
ssh newapi-16c "sudo systemctl start --wait ccmax-mysql-backup.service"
ssh newapi-16c "latest=\$(sudo find /var/lib/ccmax-manager/mysql-backups -maxdepth 1 -type f -name 'ccmax-*.sql.gz' -printf '%T@ %p\n' | sort -nr | head -1 | cut -d' ' -f2-); test -n \"\$latest\"; sudo gzip -t \"\$latest\"; sudo stat -c 'mysql_backup=%n bytes=%s' \"\$latest\""
ssh newapi-16c "sudo cp -a /opt/ccmax-manager/ccmax-manager /opt/ccmax-manager/backups/ccmax-manager-${STAMP}"
ssh newapi-16c "sudo cp -a /etc/nginx/sites-available/ccmax-manager /opt/ccmax-manager/backups/nginx-ccmax-manager-${STAMP} && sudo cp -a /etc/nginx/sites-available/ccmax-direct /opt/ccmax-manager/backups/nginx-ccmax-direct-${STAMP} && sudo cp -a /etc/nginx/sites-available/ccmax-internal /opt/ccmax-manager/backups/nginx-ccmax-internal-${STAMP}"
```

## 无感蓝绿发布

### 1. 启动临时 green 实例

临时端口固定使用 `18088`：

```bash
ssh newapi-16c "sudo systemd-run --unit=ccmax-manager-green-${STAMP} --property=User=ccmax --property=Group=ccmax --property=WorkingDirectory=/var/lib/ccmax-manager --property=EnvironmentFile=/etc/ccmax-manager.env /usr/bin/env CCMAX_ADDR=127.0.0.1:18088 CCMAX_PRICING_AUTO_SYNC=0 CCMAX_TOKEN_REFRESH_ENABLED=0 CCMAX_ACCOUNT_HEALTH_ENABLED=0 /opt/ccmax-manager/releases/${STAMP}/ccmax-manager"
ssh newapi-16c "for i in \$(seq 1 30); do curl -fsS http://127.0.0.1:18088/api/health && exit 0; sleep 1; done; sudo journalctl -u ccmax-manager-green-${STAMP} -n 100 --no-pager; exit 1"
```

green 健康检查失败时立即停止 green，不得切换 Nginx：

```bash
ssh newapi-16c "sudo systemctl stop ccmax-manager-green-${STAMP}"
```

### 2. Nginx 从正式实例切到 green

修改三个站点的 upstream，将 `127.0.0.1:8088` 替换为 `127.0.0.1:18088`，执行 `nginx -t` 成功后 reload。reload 前记录旧 worker PID；切流后必须等待这些 worker 自然退出，旧请求才算排空。不得用 `kill -9` 或提前停止正式实例。

```bash
ssh newapi-16c "pgrep -P \$(cat /run/nginx.pid) > /tmp/ccmax-nginx-workers-${STAMP}-to-green; sudo sed -i 's#127.0.0.1:8088#127.0.0.1:18088#g' /etc/nginx/sites-available/ccmax-manager /etc/nginx/sites-available/ccmax-direct /etc/nginx/sites-available/ccmax-internal; sudo nginx -t; sudo systemctl reload nginx"
```

切流后验证：

```bash
curl -fsS https://ccmax.annaapi.com/api/health
curl -fsS https://ccmax-direct.annaapi.com/api/health
ssh newapi-16c "curl -fsS http://127.0.0.1:18080/api/health"
```

等待旧 worker 排空；超时必须停止发布并保持正式实例运行：

```bash
ssh newapi-16c "for i in \$(seq 1 3600); do alive=0; while read -r pid; do kill -0 \$pid 2>/dev/null && alive=1; done < /tmp/ccmax-nginx-workers-${STAMP}-to-green; [ \$alive -eq 0 ] && exit 0; sleep 1; done; exit 1"
```

### 3. 更新正式实例

确认旧 Nginx worker 已排空后再替换正式二进制：

```bash
ssh newapi-16c "sudo systemctl stop ccmax-manager && sudo install -o root -g ccmax -m 0750 /opt/ccmax-manager/releases/${STAMP}/ccmax-manager /opt/ccmax-manager/ccmax-manager && sudo systemctl start ccmax-manager"
ssh newapi-16c "for i in \$(seq 1 30); do curl -fsS http://127.0.0.1:8088/api/health && exit 0; sleep 1; done; sudo journalctl -u ccmax-manager -n 100 --no-pager; exit 1"
```

### 4. Nginx 切回正式实例

将三个站点的 upstream 从 `18088` 改回 `8088`，再次执行 `nginx -t`、reload，并等待本次 reload 前的旧 worker 自然退出。只有 green 上的旧请求全部排空后才能停止 green。

```bash
ssh newapi-16c "pgrep -P \$(cat /run/nginx.pid) > /tmp/ccmax-nginx-workers-${STAMP}-to-main; sudo sed -i 's#127.0.0.1:18088#127.0.0.1:8088#g' /etc/nginx/sites-available/ccmax-manager /etc/nginx/sites-available/ccmax-direct /etc/nginx/sites-available/ccmax-internal; sudo nginx -t; sudo systemctl reload nginx"
ssh newapi-16c "for i in \$(seq 1 3600); do alive=0; while read -r pid; do kill -0 \$pid 2>/dev/null && alive=1; done < /tmp/ccmax-nginx-workers-${STAMP}-to-main; [ \$alive -eq 0 ] && exit 0; sleep 1; done; exit 1"
ssh newapi-16c "sudo systemctl stop ccmax-manager-green-${STAMP}; sudo systemctl reset-failed ccmax-manager-green-${STAMP} || true"
```

## 发布验证

发布结束必须检查：

```bash
ssh newapi-16c "systemctl is-active ccmax-manager; curl -fsS http://127.0.0.1:8088/api/health; sudo nginx -t; sudo journalctl -u ccmax-manager --since '-10 minutes' --no-pager"
curl -fsS https://ccmax.annaapi.com/api/health
curl -fsS https://ccmax-direct.annaapi.com/api/health
ssh newapi-16c "curl -fsS http://127.0.0.1:18080/api/health"
```

同时确认：

- `8088` 只有正式服务监听，`18088` 已释放。
- New API 的 CCMAX 渠道均指向稳定入口 `http://127.0.0.1:18080`。
- 管理页面能加载最新嵌入资源。
- `/v1/models` 使用测试用户 SK 能正常返回。
- 流式和非流式请求各完成一次真实回归，不在日志中输出完整用户 SK、Session Key、Access Token 或 Refresh Token。
- New API 的 `127.0.0.1:3000` 服务状态未被改变。

## 回滚

新版本在切回正式实例后出现问题时，先重新启动上一份二进制作为 green 并切流，再更新正式实例，仍按两次 Nginx reload 和两次 worker 排空执行。不要在有线上写入时直接恢复数据库备份。

数据库回滚只能使用已通过 `gzip -t` 和恢复演练的 MySQL 备份，并且必须先停止所有 CCMAX 实例、保留故障库副本，再由人工确认恢复；否则会丢失发布后的新增账号、计费和请求日志。
